# 共享资源与并发调度

多个 session/subagent 并行时，真正限制速度的往往不是模型，而是**同一时间只能有一个执行者的有状态资源**：一台实验虚拟机、一台开发板、一台物理设备、一个许可证、一个已登录的浏览器配置。本文件给出通用规则；具体资源、软件与数值由当次任务的环境和模板决定，文中标“举例”的只是说明。

配套工具：[scripts/resource_lock.py](../scripts/resource_lock.py)。并发上限、会话启动与卡住判定见 [多会话与子代理编排](orchestration.md) 的“多 agent 并发调度”。

## 1. 开工前先分类步骤

把已确认意图中的实施步骤逐条标注：

| 类型 | 判据 | 能否并发 | 举例（仅示意） |
| --- | --- | --- | --- |
| 独占 | 会改变同一个有状态资源；两个执行者同时操作会互相污染 | 同一资源同一时间只能一个 | 在一台实验虚拟机上改配置、启动服务、抓包 |
| 离线 | 只读材料、写文档、排版、渲染、独立审查、整理日志 | 可以多个并行 | 依据已有截图写报告；对成稿做独立审查 |

分类只看**这一步是否真的触碰共享资源**，不看任务名义上是不是“实验”。例如“启动服务并截图”是独占；“根据截图写步骤说明”是离线。占锁范围也应只覆盖实际读写资源的时间窗，而不是整个任务。

每条独占步骤还要写出资源标识（如 `vm:lab-1`、`license:仿真器`），标识相同才互斥；不同资源可各持一把锁。分类结果和执行清单一起冻结，执行中新增独占步骤要先补清单再申请锁。

## 2. 批量采集，缩短临界区

把独占步骤汇总成一张**采集清单**：一次 `acquire`，按清单连续做完所有需要现场状态的动作（启动、验证、截图、导日志、记录输出路径），然后立即 `release`。不要让锁跨过思考、写作、渲染或等待用户确认。

阿姆达尔定律给出上限：若总工作量中串行部分（必须独占或必须按序）占比为 `s`，用 `N` 个执行者时加速比不超过

```
1 / (s + (1 - s) / N)
```

`N` 增大时，收益由 `s` 决定；`s` 不降，再增加 agent 也接近 `1/s`。所以优先缩短 `s`：合并独占窗口、把只读准备和结果整理移到锁外、一次采集覆盖多个验证点。只有确认 `s` 已足够小，增加并发才有意义。

## 3. 资源成为瓶颈时的选项

按代价从低到高：

1. **复制资源**：在允许且隔离的前提下克隆环境（快照、副本容器、同配置的第二台实例）。复制后每个执行者持有独立资源，不再互斥；但共享网络、许可证服务器或外部服务仍可能成为新的单点，复制前先确认这些依赖也能分开。
2. **流水线**：A 持有资源采集时，B 处理上一批已完成的输出（写作、排版、审查）。关键是约定交接产物的路径和“可开始”条件，B 只读已完成文件，不读 A 的中间状态。
3. **拆分窗口**：把一次长时间独占拆成多个短窗口，每个窗口产出可独立验证的片段；窗口之间释放锁，让离线步骤插入。
4. **排队**：资源无法复制、也无法流水线时，用锁排队并接受串行。此时增加 agent 不提高吞吐，只增加等待与上下文成本；应减少并发，把离线步骤集中到等待期间。

不为绕过锁去并行操作同一资源；也不把“复制资源”当成默认操作，克隆、快照、额外许可证都要有用户或环境授权。

## 4. 并发上限的估算

先数出两个量：

- `R`：当前**可同时独立占用**的独占资源数。同一种资源只有一份时只算 1。
- `O`：输入已就绪、可以离线执行的步骤数，包括各自独立的写作、渲染与审查上下文。依赖某个独占步骤输出的离线步骤，在产物出现前不计入。

再取宿主和用户允许的并发槽位数 `S`。起始并发按

```
N ≈ min(S, R + O)
```

其中独占侧最多 `R` 个同时工作，其余槽位给离线步骤；`O` 大于剩余槽位时排队。运行中观察：若大部分会话在等锁，说明瓶颈是 `R`，应先复制资源或改流水线；若锁空闲而队列仍长，瓶颈是 `S` 或离线步骤之间的依赖，应拆分产物或减少串行确认点。

这是估算规则，不是固定数字。实际取值还要满足：审查必须由独立上下文完成、同一产物只能有一个写者、用户确认点不能被并发绕过。

## 5. 锁、心跳与失效

独占资源用 `resource_lock.py` 的记录，不靠“我记得没人用”。

```
python -B scripts/resource_lock.py acquire --lock WORK/locks/vm-lab-1.lock \
    --owner writer-a --pid <native-pid> --lease 120
python -B scripts/resource_lock.py renew   --lock ... --owner writer-a
python -B scripts/resource_lock.py release --lock ... --owner writer-a
python -B scripts/resource_lock.py status  --lock ... [--owner writer-a]
python -B scripts/resource_lock.py break-stale --lock ... --owner dispatcher \
    --reason "pid 已不存在且心跳过期"
```

规则：

- **原子创建**：锁文件已存在时 `acquire` 失败，绝不覆盖；先 `status`，再决定等待还是处理失效。
- **只有 owner 能续期和释放**：`renew`/`release` 比对记录中的 owner；不要替别人释放，也不要手工删除锁文件充当释放。
- **失效只有两个判据**：心跳超过 `lease_seconds`，或记录中的 pid 在本机已不存在。两者都不满足时不得判失效；`break-stale` 必须给原因，并追加到 `<lock>.log`。
- **fencing token 单调递增**：每次成功持有都取得更大的 token。把 token 写进产物名、清单或结果记录；旧的持有者恢复后若发现当前 token 更大，就丢弃自己的迟到写入，而不是覆盖新结果。`<lock>.fence` 保存计数，不要随手删除，删除会让序号回退。
- **主机范围**：只有记录 host 与本机一致时才检查 pid；远程主机只能靠租约判定。多机同名时改用带唯一标识的 host 标签或每机独立锁路径。
- **CLI 与进程**：`acquire` 的 `--pid` 要写**长驻的持有者**的原生 PID（PowerShell `$PID`，POSIX shell `$$`），不是一条执行完就退出的命令；Git Bash/MSYS 等兼容层的 `$$` 可能是伪 PID，此时改用原生进程 PID，或由会话直接 import 记录 `os.getpid()`。否则记录会立刻被判为 pid 消失。
- **锁的位置**：放在任务工作目录，不放技能安装目录；锁只保护资源，不传递任务进度或授权。

持锁进程崩溃会留下锁文件，这是设计行为：由调度者检测失效、记录原因后 `break-stale`，再由下一个执行者重新 `acquire`。正常结束必须 `release`，不能用“反正会过期”替代。

## 6. 反例

- 一边持锁一边等用户确认或写整篇报告，把临界区拉成整个任务。
- 两个会话同时写同一个 `state.json`、同一份成稿或同一个输出目录。
- 看到锁“很久没动”就直接删文件，不查心跳和 pid，也不留原因。
- 把“并发数固定为 3/4/5”写进流程；并发数应由 `R`、`O`、`S` 当次算出。
- 为了并行而复制环境，却共用同一个许可证服务或同一份外部状态。
- 旧会话恢复后继续写，覆盖了已由更新 token 完成的结果。
