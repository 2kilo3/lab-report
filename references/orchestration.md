# 多会话与子代理编排

本文件说明如何把同一任务切成**认知上下文**：材料阅读、意图、执行、写作、独审、修订各用相对独立的 session/subagent，避免长会话腐烂、旧结论污染和跨段偷懒。切的是上下文，不是权限，也不是实验环境。

## 1. 原则

- **一个编排者写状态**：`state.json` 只由主编排会话写；子代理返回结果，不各自改状态、不各自确认意图。
- **共享环境仍只有一个执行者**：同一有状态 VM/实验环境同一时间只允许一个执行者操作；并行只用于只读阅读、独立审查或互不依赖的独立实例。
- **选择性共享短上下文**：每段只拿完成本段所需的最少材料、索引和结论引用；不把完整聊天记录、全部材料或上一段的自我评价整包转交。
- **原始依据优先**：下游需要事实时按 `map_id`/文件定位回读原文；上游总结只能当索引，不能当证据。
- **经验层不是调度总线**：`memory` 只保存经批准的方法经验，不用来传递任务进度、待办、确认或“上一会话说过了”。调度与状态以任务工作记录、`MATERIALS_MAP.md` 和 `PROGRESS.md` 为准。

## 2. 分段与输入

| 段 | 典型上下文 | 主要输入 | 主要输出 | 不拿什么 |
| --- | --- | --- | --- | --- |
| 材料阅读 | 每份关键材料一个 subagent/新 session | 单一材料、返回字段、地图骨架 | `map_id` 索引条目与短引文 | 用户历史聊天、未确认意图、写作草稿 |
| 意图确认 | 主编排 session | 完整材料地图、用户补充要求、经验展示 | 已确认意图 MD（每条带 `map_id`） | 执行细节草稿、旧版通过结论 |
| 执行 | 按段新 session（下载/配置、拓扑、抓包、服务验证等） | 已确认意图切片、冻结 Step Card、环境说明 | 逐步证据与 `complete_step` 结果 | 写作规则全文、其他段未完成结论 |
| 写作 | 新 session | 意图、模板允许区、地图相关条目、Evidence Binder、写作规则 | 当前候选文档 | 全部执行聊天、后台命令流水 |
| 独审 | 独立 subagent/新进程 | 见 §3 白名单 | REVIEW 表与审核收据 | 制作方摘要、历史“已通过”、未授权内部日志 |
| 修订 | 干净 session | REVIEW 表相关行、受影响片段、当前候选、对应证据 | 局部修订与复核记录 | 整份历史对话、无关章节旧稿 |

同一段内可以连续工作；跨段默认新上下文。纯审查任务不强行拆执行段。

## 3. 审查输入白名单

独审只接收下列内容；白名单外材料需说明用途并经编排者确认，不能以“方便判断”为由整包投喂。

| 允许 | 说明 |
| --- | --- |
| 原始任务/模板/评分/指导书/范例 | 按实际文件或可定位摘录；关键原文可回读 |
| `MATERIALS_MAP.md` | 索引与 `map_id`，用于核对意图覆盖 |
| 已确认意图 MD | 当前版本及其确认引用 |
| 冻结 Step Card 与逐步证据绑定 | 执行步骤、`must_include` 验收和证据路径 |
| 当前成稿与最终渲染页面 | 由最终候选生成，不是旧 PDF/旧预览 |
| 实际采用的证据原图/日志 | 与对象、轮次、代码配置对应 |
| 实际采用的 lessons 记录 | 仅方法经验，见 [经验协议](memory.md) |

| 不允许 | 原因 |
| --- | --- |
| 制作方的“已完成/没问题”总结 | 预灌通过结论，破坏独立性 |
| 历史独审通过记录、旧版本收据 | 只证明旧版本 |
| 未展示给用户的候选经验、内部草稿 | 未批准内容不能成为依赖 |
| 无关任务/其他学生/私人材料 | 越界与隐私风险 |
| 完整聊天记录或工具流水 | 噪声大，且可能夹带未核实断言 |

白名单不扩大权限：读取受保护材料、上传、安装、创建凭据仍按宿主授权。

**机器检查点**：独审开始前先运行 `python -B scripts/workflow_state.py --state <任务目录/state.json> --request <review-gate.json>`，其中请求为 `{"action":"review_gate","required":["<渲染页或原图路径>", "..."]}`；`record_review` 会在接收收据前自动执行同一检查。缺材料地图、意图、冻结卡/逐步证据、成稿或 `required` 路径时非零退出并一次列出缺项。该检查只证明产物在位，不能替代把原始材料交给独立上下文。

## 4. 审查产物：REVIEW 表

独审输出必须能直接驱动修订，而不是一段散文。每条问题一行：

| 问题 | map_id / 意图条 / 图或段落 | 严重度 | 应改动作 | 是否阻断 |
| --- | --- | --- | --- | --- |
| 截图未显示 Postman 窗口，只有 curl 输出 | M3；意图 §一.3；图 5 | 高 | 按指导书在 Postman 重发并重截，curl 仅留后台核对 | 是 |
| 小节标题被改为黑体并放大 | M2；样式 §二；§2.1 标题 | 中 | 恢复模板中文字体与字号，仅加粗 | 否 |

- 定位必须能回到 `map_id`、意图条目或具体图/段落；写不出定位的意见标“待核实”，不能直接要求改稿。
- 严重度用高/中/低，并说明影响；`是否阻断` 决定能否进入交付。
- 结论区分通过、已证实问题、缺证据、未验证、不适用；不能把“没查”写成“不适用”。
- 审查者不直接改正文；制作方核实依据后修订，再由独立审查复核原问题与关联影响。

## 5. 修订用干净会话

修订默认开新 session，只带：

1. REVIEW 表中本轮要处理的行；
2. 对应 `map_id`、意图条目、图号/段落和证据路径；
3. 当前候选文档及允许编辑区域；
4. 受影响执行卡的局部范围。

修订规则：

- **按 REVIEW 局部解冻**：只重开被点名的步骤/段落；不默认整轮重做实验或整篇重写。
- 证据问题回到对应执行段补采，再重新 `complete_step`；排版问题只回排版，不重跑实验。
- 修改后复核原问题及关联影响（图号、引用、分页、样式继承），并把复核结果交回独审。
- 新发现超出 REVIEW 范围时，先记录并判断是否改变意图；不静默扩改。

## 6. 文件分工

| 文件/载体 | 放什么 | 不放什么 |
| --- | --- | --- |
| `CLAUDE.md` / `AGENTS.md` | 项目长期规则、目录约定、稳定命令 | 本次进度、临时待办、逐轮实验日志 |
| `PROGRESS.md` | 当前阶段的简短进度、阻塞、下一步；有界追加 | 完整对话、证据全文、未经确认的结论 |
| `state.json` + Step Card 记录 | 权威阶段、确认、冻结卡、逐步证据 | 模型自述“已完成”替代状态 |
| `MATERIALS_MAP.md` | 材料索引与影响范围 | 材料全文复制 |
| 任务产物目录 | 意图 MD、执行卡、证据、候选文档、REVIEW 表 | 技能安装目录内的任务数据 |
| 经验 memory | 经批准的方法经验与来源 | 任务调度、进度、确认或待办 |

`PROGRESS.md` 只是接手提示，不是授权或验收记录；恢复时仍先核对实际文件与状态。

## 7. 交接包（handoff packet）

跨段转交用短包，建议不超过一屏：

```markdown
- 任务与目标：[一句话]
- 当前阶段：[材料/意图/执行/写作/独审/修订]
- 已确认意图：[路径 + 版本/摘要]
- 相关地图条目：[map_id 列表，不贴全文]
- 冻结步骤与证据：[step id → evidence id]
- 本轮限制：[用户明确禁止项、权限边界]
- 待处理：[REVIEW 行号或具体问题]
- 不要做：[不重跑、不扩范围、不改模板保护区等]
```

不把上一段的推理过程、失败尝试全文或自我评价放进交接包；需要时给可定位引用。

## 8. 失效与恢复

- 材料或意图变化：下游写作、独审、修订段全部失效；按 [材料地图](materials-map.md) 更新并判断哪些执行步骤需重做。
- 执行卡改卡：清除受影响步骤记录，重新冻结；只让受影响段重开。
- 成稿变化：旧 REVIEW 结论不能直接复用；先判断影响，再局部重审。
- 子代理返回与原文冲突：以原文为准，记录冲突，不把子代理总结升级为事实。
- 会话中断：先读 `state.json` 的 `status`、实际卡与证据，再决定从哪段恢复；不凭聊天记忆续做。

## 9. 反例

- 把全部材料、全部聊天记录和旧审查结论塞给写作或独审 session。
- 每个子代理各自写 `state.json` 或各自“确认”意图。
- 用 memory 记录“下一步该做什么”，恢复时把经验当进度。
- 独审只拿到制作方摘要，没拿原始材料和当前成稿。
- 修订 session 拿到 REVIEW 后整篇重写，或没改的步骤也重跑。
